### What the manifest does not record

Whether a capability works with an **application** identity, a
**delegated** one, or both. Every collected row above is therefore
`not established` on that column, and the candidate rows below carry it
because their sources publish it. This is a real gap: the difference
decides whether a capability can run unattended, and it is currently
discoverable only by running the collector.

### `entra-authentication-method-registration`

Which authentication methods each user has actually registered, as opposed to which the tenant permits.

*Could be asked:*

- how many accounts are capable of multifactor authentication rather than merely permitted it
- are the accounts holding privileged roles among them

**Known limitation.** the report excludes disabled users, so an absent account is not an unregistered one. It returns userPrincipalName and userDisplayName, which this engine avoids collecting elsewhere, so a collector reading it takes on an identifier-handling decision the rest of the catalogue does not have. Feature licensing is documented separately from the API.

Schema: present in v1.0, beta, checked 2026-08-24.

Authority: <https://learn.microsoft.com/graph/api/authenticationmethodsroot-list-userregistrationdetails?view=graph-rest-1.0>, read 2026-08-24.

### `entra-authentication-methods-policy`

Which authentication methods the tenant permits, and whether registration is enforced at sign-in.

*Could be asked:*

- which methods are enabled for the whole tenant, and which are enabled for a subset
- is registration enforcement switched on
- is the tenant still governed by the legacy MFA and SSPR policies

**Known limitation.** policyMigrationState changes what the policy governs -- authentication only, authentication and SSPR, or legacy policies ignored -- so the same document means three different things and a rule that does not read the state is reading a value out of context. Not available in China operated by 21Vianet.

Schema: present in v1.0, beta, checked 2026-08-24.

Authority: <https://learn.microsoft.com/graph/api/authenticationmethodspolicy-get?view=graph-rest-1.0>, read 2026-08-24.

### `entra-cross-tenant-access-default`

What the tenant allows by default with every organisation it has not configured individually.

*Could be asked:*

- is inbound or outbound collaboration open by default
- is the tenant carrying the service default or a configuration somebody made

**Known limitation.** several of the roles that grant this read return basic properties only and exclude identity synchronization settings. The call returns 200 and the response is incomplete, so a partial read is indistinguishable from a full one unless the collector records which role read it -- exactly the collapse a refusal fixture exists to prevent, arriving as a success rather than a denial.

Schema: present in v1.0, beta, checked 2026-08-24.

Authority: <https://learn.microsoft.com/graph/api/crosstenantaccesspolicyconfigurationdefault-get?view=graph-rest-1.0>, read 2026-08-24.

### `entra-role-eligibility`

Who is eligible to activate a directory role, as distinct from who currently holds one.

*Could be asked:*

- does the count of standing Global Administrators understate who can become one
- is privileged access time-bound or permanent

**Known limitation.** Privileged Identity Management requires Microsoft Entra ID P2 or an EMS E5 licence. In a tenant without it the surface returns nothing, and nothing means `not licensed` as readily as `nobody is eligible` -- so an empty response cannot be reported as an absence of eligibility.

Schema: present in v1.0, beta, checked 2026-08-24.

Authority: <https://learn.microsoft.com/graph/api/rbacapplication-list-roleeligibilityscheduleinstances?view=graph-rest-1.0>, read 2026-08-24.

### `exchange-unified-audit-ingestion`

Whether the unified audit log is ingesting at all.

*Could be asked:*

- is anything being recorded to audit against

**Known limitation.** the same cmdlet exists in Security and Compliance PowerShell, where the property is documented as always False even when auditing is on. Two consoles, one cmdlet name, two answers, and only one of them is about the tenant -- so which console made the call is part of the evidence and not an implementation detail. The Audit Logs role governs turning auditing on or off.

Authority: <https://learn.microsoft.com/purview/audit-log-enable-disable>, read 2026-08-24.

### `exchange-organization-config`

The organisation-wide Exchange Online settings, including whether mailbox auditing is switched off for the tenant.

*Could be asked:*

- is mailbox auditing disabled organisation-wide, which makes every per-mailbox audit setting inert

**Known limitation.** Exchange publishes no per-parameter permission table and directs the reader to determine the required permissions in their own organisation; the read-only shape is the View-Only Configuration role. Least privilege here is established per tenant rather than from a page, so this row stays `not-established` until it is measured.

Authority: <https://learn.microsoft.com/powershell/module/exchangepowershell/get-organizationconfig?view=exchange-ps>, read 2026-08-24.
